Git Mystery learner guide

Follow these steps in order. Read the matching concept slides, do the work in your terminal and editor, then refresh the dashboard. The evidence and Git history contain the mystery answers.

Run Git commands from the repository root in a second terminal. Keep the terminal running bun run start open throughout the activity. Replace capitalized placeholders with your own values.

M0 · Arrive and launch

git clone https://github.com/universitysjp/git-mystery.git
cd git-mystery
bun install
bun run start

The slides open on port 3030 and the dashboard on port 3031. If browser opening is unavailable, open the two URLs printed in your terminal. Open the cloned folder in your editor and locate activity/case/.

Expected state: the dashboard detects a Git checkout. Only edit the case files during the investigation.

M1 · Publish a baseline

  1. On GitHub, create a repository in your own account. Leave it empty: do not initialize a README, license, or ignore file.
  2. Copy that repository's HTTPS or SSH URL. Replace YOUR_REPOSITORY_URL below with it.
git remote rename origin starter
git remote add origin YOUR_REPOSITORY_URL
git remote -v
git push -u origin main

starter points to the workshop repository; origin points to your own repository. Sign in through your Git credential manager if prompted. Refresh the dashboard after the push.

Expected state: your GitHub repository contains the starter files and history, and M1 is solved.

M2 · Inspect the case

  1. Read the case README, clues, and summary in your editor.
  2. Check the present state and scan the commit history.
git status
git log --oneline
git show COMMIT_ID

Replace COMMIT_ID with the short hash of a relevant handover-note commit. Read its diff, including removed lines. Find who signed off the briefing and at what time; record your answer in the dashboard.

Expected state: the working tree is clean and the history observation is accepted. The guide does not supply that observation.

M3 · Make a local finding

Edit activity/case/findings.md and record the finding you recovered from history. Save the file, then inspect your edit:

git status
git diff

Read the removed and added lines. In the dashboard, capture the local diff with Check step and answer the diff question. Keep the change unstaged until the next mission.

Expected state: Git reports the case file as modified, and M3 is solved after your answer.

M4 · Save the finding

git add activity/case/findings.md
git diff --staged

Before committing, click Check step in the dashboard to capture this staged state. Then record and share the snapshot:

git commit -m "Record first finding"
git log --oneline
git push

Expected state: the finding appears in a commit on your GitHub main. Refresh the dashboard.

M5 · Prepare two leads

Both branches must start from the same pushed main. Create A first:

git switch main
git status
git switch -c lead-a

In activity/case/summary.md, replace the value of the - Final briefing sign-off: line using the history clue. Leave the surrounding case text intact.

git diff
git add activity/case/summary.md
git commit -m "Propose lead A"
git push -u origin lead-a
git switch main
git switch -c lead-b

On B, replace the same line using the courier manifest clue. The line still starts from the original pending value because you returned to main before creating B.

git diff
git add activity/case/summary.md
git commit -m "Propose lead B"
git push -u origin lead-b

Expected state: two independently pushed branches with different supported edits to the same line. Do not merge either yet.

M6 · Open two pull requests

  1. In your GitHub repository, choose Pull requests → New pull request.
  2. Set the base to main and compare to lead-a. Review the diff and create the PR.
  3. Repeat with base main and compare lead-b.
  4. Record the two different PR URLs in the dashboard and confirm you opened and reviewed each.

Expected state: both PRs are open before the first merge. The dashboard labels these GitHub actions self-confirmed because it does not access your account.

M7 · Encounter and resolve

Merge PR A on GitHub using Create a merge commit, rather than squash or rebase. Keep both branch names available through the exercise. PR B should now report a conflict.

git switch main
git pull
git switch lead-b
git merge main

Git stops with a conflict in the case summary. Run git status and click Check step in the dashboard while that conflict is active.

  1. Open the summary in your editor. Read both versions between the conflict markers.
  2. Re-read the evidence and write one designated summary line carrying both supported findings.
  3. Delete every <<<<<<<, =======, and >>>>>>> marker line, including the marker labels. Save the file.
git add activity/case/summary.md
git status
git diff --staged
git commit -m "Resolve the briefing conflict"
git push

git add tells Git the file is resolved. Status clears the unmerged path after staging; it may still say you are merging until you commit. Refresh the dashboard after the push.

Expected state: B contains the committed resolution and its PR is mergeable on GitHub.

M8 · Finish and retrieve

Merge PR B on GitHub using Create a merge commit, then retrieve the final result:

git switch main
git pull
git status
git log --oneline --graph

Read the committed summary, check that every conflict marker is gone, and answer the recall question in the dashboard. Refresh to see all missions solved and your learned concepts.

Expected state: local main contains both merges, the working tree is clean, and the dashboard shows 9 of 9 solved.

Recovery help

Git says a branch has no upstream

For a branch's first push, name it explicitly: git push -u origin lead-a or git push -u origin lead-b. Later pushes from that branch can use git push.

B was created from A

Pause before merging. Preserve the mistaken branch under a backup name, then recreate B from the unchanged main used for A:

git switch main
git branch -m lead-b lead-b-backup
git switch -c lead-b

Reapply only the manifest finding to the designated line, inspect the diff, stage it, and commit. If the mistaken B was already pushed or has a PR, ask the facilitator to help preserve it and replace the remote branch before publishing the corrected B. Keep the backup until the exercise is complete.

The conflict was resolved before capturing it

Keep your work. Ask the facilitator to help replay the conflict in a safe copy. The app requires observing a real conflict and will not accept an ordinary proposal as a resolution.

The working tree is still unmerged after editing

Remove all markers, save, then git add activity/case/summary.md. Run git status again and commit when it says the conflicts are fixed.

The final GitHub merge is missing locally

Run git switch main and git pull. If Git refuses because of local edits, preserve those edits before switching; use git status and ask for help.

An answer or checkpoint was rejected

Read the feedback, check the current Git state, and retry. Do not reset progress to fix a Git mistake: resetting only clears local dashboard answers and checkpoint records.

A push cannot authenticate

Check git remote -v and sign in through your credential manager. GitHub account passwords are not accepted for HTTPS Git pushes. The prerequisites guide covers account setup.

A port is already occupied

Close the earlier workshop process with Ctrl+C, or close the app using port 3030 or 3031, then retry. On macOS inspect it with lsof -i tcp:3030; on Windows use Get-NetTCPConnection -LocalPort 3030. Substitute 3031 for the dashboard port.
